Temas técnicos

Diez temas de apoyo: por qué importan, qué conviene dominar y qué cursos los cubren.

Estos temas no son pasos ni requisitos

Lo que hay que hacer y en qué orden lo marca el plan oficial. «Qué conviene dominar» son ideas para orientarte, no una lista que tengas que cumplir. En cada tema, los cursos del track de DataCamp los harás en el paso 2 del plan; los de para profundizar son opcionales.

Python y APIs

Por qué importa

Antes de añadir IA necesitas un servicio Python limpio, con un contrato claro y pruebas: muchos fallos son de ingeniería corriente, no del modelo.

Qué conviene dominar

  • Organizar un proyecto Python en módulos, con pruebas que se ejecuten desde un entorno limpio.
  • Exponer una API con FastAPI validando la entrada.
  • Separar la capa HTTP de la lógica de negocio.

Relación con el plan: DataCamp y los dos proyectos, que usan LangChain y FastAPI.

Cursos de este tema

Del track de DataCamp:

  • Software Engineering Principles in Python

Para profundizar (opcional):

  • Introduction to FastAPI

LLM y contexto

Por qué importa

Es la base de cualquier aplicación con un modelo. El trabajo consiste en controlar qué entra (instrucciones y contexto) y qué sale (una respuesta validada), porque el modelo puede sonar convincente y estar equivocado.

Qué conviene dominar

  • Llamar a un modelo pasándole un fragmento de contexto explícito.
  • Comparar dos versiones de un prompt sobre unas pocas preguntas fijas.
  • Exigir una salida con esquema válido y controlar timeouts y fallos del proveedor.
  • Explicar por qué un buen tono no demuestra que la respuesta sea verdadera.

Relación con el plan: DataCamp y Proyecto 1.

Cursos de este tema

Del track de DataCamp:

  • LLMOps Concepts
  • Working with the OpenAI Responses API

Para profundizar (opcional):

Embeddings y RAG

Por qué importa

El modelo no conoce los documentos de tu organización. En vez de reentrenarlo, en cada pregunta se le da la parte relevante de tus documentos (RAG): es la base de casi cualquier asistente de conocimiento interno.

Qué conviene dominar

  • Indexar documentos por secciones con embeddings, de forma repetible.
  • Recuperar fragmentos (top-k) y citar de dónde sale cada afirmación.
  • Excluir de las búsquedas activas las versiones obsoletas.
  • Distinguir si un fallo viene del buscador o de la generación, y abstenerse cuando no hay evidencia.

Relación con el plan: DataCamp y Proyecto 2, el chatbot con RAG.

Cursos de este tema

Del track de DataCamp:

  • Introduction to Embeddings with the OpenAI API
  • Building AI Applications with Pinecone
  • Developing LLM Applications with LangChain

Evaluación

Por qué importa

Sin medir no sabes si un cambio mejora o empeora el sistema. Con unas pocas preguntas fijas puedes comparar dos versiones de tu proyecto y saber qué aporta cada cambio.

Qué conviene dominar

  • Preparar unas preguntas para ajustar el sistema y otras guardadas aparte para la comprobación final.
  • Reproducir la comparación entre dos configuraciones de recuperación o de prompt.
  • Explicar por qué las preguntas guardadas aparte no se usan para elegir la mejor configuración.
  • Registrar en cada etapa un identificador de petición, la duración, los errores y el consumo.

Relación con el plan: no es requisito. Es útil para comprobar si tus proyectos responden bien.

Cursos de este tema

Para profundizar (opcional):

  • LLM Application Evaluation with LangSmith

Herramientas y LangGraph

Por qué importa

Las herramientas dejan que el asistente consulte sistemas reales, no solo documentos. Cada grado de autonomía añade coste y riesgo: añade solo el que puedas justificar frente a un flujo fijo más simple.

Qué conviene dominar

  • Definir una herramienta de solo lectura con contrato estricto de entrada y salida.
  • Construir un grafo de LangGraph con estado para consultas documentales, de datos o mixtas.
  • Garantizar que el ámbito autorizado lo fija la aplicación, no el modelo.
  • Poner límites (número de invocaciones, timeouts) y comprobar qué pasa al agotarlos.

Relación con el plan: DataCamp toca las herramientas y los agentes. Usarlos en tus proyectos es opcional, no es requisito.

Cursos de este tema

Para profundizar (opcional):

  • LLM Tool Use with LangChain
  • Agentic Systems with LangGraph

MCP y conectores

Por qué importa

MCP es un protocolo común para que un asistente use herramientas ajenas a su código. Sacar una consulta a un conector la hace reutilizable, pero hay que comprobar que no se pierden los controles de permisos.

Qué conviene dominar

  • Exponer una consulta como servidor MCP local.
  • Consumirla desde el asistente con la misma respuesta y los mismos permisos.
  • Rechazar argumentos inválidos y devolver un error controlado si el servidor no está disponible.
  • Explicar dónde se conserva el contexto de autorización y cómo se aísla entre identidades.

Relación con el plan: DataCamp tiene un curso de MCP. Usarlo en tus proyectos es opcional.

Cursos de este tema

Del track de DataCamp:

  • Introduction to Model Context Protocol (MCP)

API segura y Docker

Por qué importa

Un servicio que van a usar otras personas conviene protegerlo (quién pregunta y qué puede ver) y empaquetarlo para que se ejecute igual en cualquier sitio.

Qué conviene dominar

  • Autenticar y autorizar peticiones, y acotar el tamaño de entradas y respuestas.
  • Evitar que los errores filtren detalles internos.
  • Construir una imagen Docker reproducible que no se ejecute como administrador.
  • Probar casos negativos: credencial inválida, datos de otra área e instrucciones ocultas en un documento.

Relación con el plan: los dos proyectos exponen una API con FastAPI. Protegerla a fondo y empaquetarla con Docker es opcional.

Cursos de este tema

Para profundizar (opcional):

  • Deploying AI into Production with FastAPI
  • Introduction to Docker

AWS en el programa

La nube se practica en AWS Cloud Quest, un laboratorio en el que despliegas recursos reales sin coste para ti. El plan no pide una cuenta propia de AWS ni desplegar tus proyectos en ella. Los tres temas siguientes sirven para entender lo que verás allí y para ir más allá si quieres.

AWS, identidad y coste

Por qué importa

Un asistente acaba en la nube y consumiendo APIs de pago. Entender servicios, permisos y límites de gasto evita las sorpresas habituales.

Qué conviene dominar

  • Distinguir el rol de ejecución de una tarea de los permisos de la aplicación.
  • Saber qué servicios, región y datos intervienen en una arquitectura sencilla.
  • Explicar por qué una alarma de presupuesto avisa pero no corta el gasto.
  • Describir cómo detener tareas y retirar recursos al terminar.

Relación con el plan: AWS Cloud Quest.

Cursos de este tema

Para profundizar (opcional):

  • AWS Concepts
  • AWS Cloud Technology and Services Concepts
  • AWS Security and Cost Management Concepts

Despliegue en AWS

Por qué importa

Un asistente solo es útil si otros pueden usarlo. Conviene ejecutar en la nube el mismo artefacto que probaste, con un pipeline que bloquee la publicación si fallan las pruebas y una forma clara de volver atrás.

Qué conviene dominar

  • Publicar una imagen en ECR y ejecutarla en Fargate, con logs y secretos por referencia.
  • Reproducir la infraestructura con CloudFormation, no a mano.
  • Montar un pipeline que pruebe, construya y exija aprobación para publicar.
  • Hacer rollback a un artefacto anterior y retirar los recursos propios.

Relación con el plan: en AWS Cloud Quest desplegarás recursos en un laboratorio. Lo demás es opcional.

Cursos de este tema

Para profundizar (opcional):

  • Introduction to AWS Boto in Python
  • Deploying Applications on AWS
  • Automating Deployments on AWS

Operación

Por qué importa

Un sistema no está terminado hasta que puede operarse y diagnosticarse. Conviene saber qué mide, cómo falla y cómo se recupera.

Qué conviene dominar

  • Configurar métricas, logs y una alarma útil en CloudWatch, y enlazar el identificador de petición con la traza.
  • Volver a pasar tus preguntas de prueba después de cada cambio y saber cómo recuperar el servicio si falla.
  • Identificar dónde se consumen el tiempo y el coste.
  • Dejar documentación con la que otra persona reproduce y verifica el sistema.

Relación con el plan: no es requisito. Si ya dominas estos temas, puedes añadir Langfuse a tus proyectos para ver las trazas.

Cursos de este tema

Para profundizar (opcional):

  • Monitoring and Troubleshooting AWS

Consejos para tus proyectos

Son ideas basadas en buenas prácticas técnicas, no requisitos. Úsalas si te ayudan.

  • Cita las fuentes: cada afirmación de la respuesta debería poder rastrearse a un fragmento concreto.
  • Abstente cuando no haya evidencia: es mejor «no lo sé» que una respuesta verosímil inventada.
  • Evalúa por separado la recuperación y la respuesta, con un puñado de preguntas fijas. Así sabes si el fallo está en la búsqueda o en el modelo.
  • Pon las reglas de seguridad en el código y no solo en el prompt: el modelo puede ser engañado, tu código no debería.
  • Mantén las claves fuera del código (variables de entorno o gestor de secretos) y fuera de los logs y del repositorio.
  • Añade trazas por petición, con un identificador que aparezca en la respuesta y en los logs.
  • Empieza con un flujo fijo antes de pasar a un agente: es más barato, más rápido y más fácil de probar.
  • Pon límites de llamadas y timeouts a modelos y herramientas, para evitar bucles y gastos inesperados.
